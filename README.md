## Проверки

    npm run check                      # типы + линт + тесты (36 тестов)
    npx tsx scripts/check-baileys.ts   # связка с библиотекой WhatsApp
    npx tsx scripts/check-db.ts        # миграции и гарантии схемы на живой базе

`check-baileys` запускать обязательно после каждого обновления Baileys —
он ловит пропавшие экспорты и несовместимость хранения ключей сессии.

`check-db` требует пустую тестовую базу, например:

    docker run -d --rm --name pg-test -e POSTGRES_USER=test \
      -e POSTGRES_PASSWORD=test -e POSTGRES_DB=test -p 55433:5432 postgres:16-alpine
    PGHOST=127.0.0.1 PGPORT=55433 PGUSER=test PGPASSWORD=test PGDATABASE=test \
      PUBLIC_DOMAIN=x REDIS_URL=redis://127.0.0.1:6379 ADMIN_API_KEY=test-key \
      npx tsx scripts/check-db.ts

## Временный пароль в админку

Номер, который подключаем, часто принадлежит не владельцу аккаунта:
телефон у сотрудника, а QR живёт меньше минуты и пересылать его картинкой
бесполезно — человек должен открыть админку сам. Общий пароль ему давать
плохо: он один на всех и потом придётся менять всем.

Поэтому в админке есть «Временный пароль»: обычный вход, но на несколько
часов и с отзывом в одно нажатие. Отзыв срабатывает сразу, даже если
страница у человека уже открыта. Пароль показывается один раз — у нас
остаётся лишь его отпечаток. Единственное, чего под ним нельзя, — выдать
ещё один временный пароль: иначе временный доступ продлевал бы себя сам.

## Известные особенности, проверенные живьём

- **Подпись запросов к amoCRM** считается по пути БЕЗ строки параметров.
  С параметрами — 403. В их документации этого нет.
- **Вебхуки amoCRM** подписаны способом, который подобрать не удалось:
  перебрано больше 800 сочетаний. Пока проверка идёт по адресу, который
  содержит scope_id.
- **Имя собеседника** в чате amoCRM берёт из карточки контакта, наше
  игнорирует. Пометки мессенджера в имени бесполезны.
- **Беседу, начатую менеджером из карточки**, amoCRM заводит свою — без
  нашего conversation_id. Связать её с нашей нельзя, но писать в неё
  можно: в `new_message` вместо `conversation_id` указывается
  `conversation_ref_id` с её идентификатором. Иначе ответ клиента уходит
  в нашу беседу, оказывается в другой карточке, и amoCRM заводит под него
  вторую сделку.
- **Один и тот же человек легко становится двумя контактами**: заявка
  с сайта приходит с номером в своём виде (`966 038-88-83`), мессенджер
  даёт его же в международном (`79660388883`). Поиск в amoCRM их роднит,
  а вот новый чат сам к старому контакту не привяжется.
- **MAX не присылает телефон** собеседника — связать с существующим
  контактом по номеру нельзя.
- **В MAX нельзя завести переписку**: её номер вычисляется из номеров
  двух собеседников (побитовое исключающее или). Поэтому написать первым
  можно всегда, но слать нужно именно в переписку: по номеру человека MAX
  ищет собеседника с таким номером переписки, не находит и молчит.
- **Время сообщения MAX — в миллисекундах**, а не в секундах, как принято.
  Если умножить его ещё раз, получается пятьдесят восьмое тысячелетие,
  и база отказывается принимать запись: входящее теряется целиком.
  Именно это, а не обрывы связи, съедало входящие MAX.
- **Служба MAX отправляет только файл с диска** — ей нужен размер.
  amoCRM же присылает ссылку, поэтому файл сначала скачиваем в общий том.
- **Начать разговор из карточки** amoCRM позволяет не всегда: если
  собеседника в канале ещё нет, выбора чата может просто не быть.
  Что именно ей нужно — выясняется.
- **Эхо своей отправки** приходит из мессенджера за миллисекунды и
  обгоняет запись в базу, поэтому отправленное помечается в памяти.
